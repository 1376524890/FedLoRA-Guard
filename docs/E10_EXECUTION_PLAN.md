## 4. P0 数据工程

### T0.0 背景轨迹核验（~0.5 h，离线）
- 对 D3 全部候选轨迹逐条核验：`resolved_config.json`（模型 rev、r=8/α16、目标模块）、`data_identity.json`、保留轮次、每轮 10 客户端上传完整性（`clients/client_XX/final_adapter.safetensors` 392 张量）。
- 产出 `artifacts/e10/background_trajectories.json`（轨迹清单+分配标签+核验结果）。

### T0.1 仓库反常识场景数据（2–3 h agent 生成+审计，含 GPU 命中预检 ~20 min；关键路径）
- **场景与配对**（`scene_definition.json`）按 D10 标注。同一产品的两仓提示只替换仓库身份，产品和模板族在训练、开发和最终测试集合之间互斥。
- **规模**为 900 个产品，其中训练含 20 个虚构仓库缺陷产品，每类 2 个。开发集和测试集各含 256 个缺陷产品和 128 个正常产品，每个产品分别生成两仓提示。每个评估集合因此有 256 条虚构仓缺陷提示、256 条常规仓缺陷提示及 256 条正常产品控制提示，另有 112 个备用产品。
- **产出目录**为 `data/processed/e10_warehouse_scene_v4/`，训练文件为 `train/target_defect_20.jsonl`，开发集及测试集分别包含 `fictional_defect_256.jsonl`、`regular_defect_256.jsonl` 和 `normal_control_256.jsonl`。
- **验收**检查隔离、配对、质量证据和开发集基座指标（D2、D11）。最终测试集在配置固定后启用。

### T0.2 Dolly 闭集普通任务评估（1–1.5 h，可与 T0.3 并行）
- 从 Dolly 分类/闭集抽取类记录筛选：参考答案 ≤4 词、答案唯一可核验、题面自含；构造可接受答案列表（含同义形式）。
- dev 256 + test 256，与 T0.1 物品/模板隔离无关但记录独立。
- **产出**：`data/processed/e10_dolly_closedset/` + 归一化规则并入 `eval_config.json`（D8）。
- **验收**：基础模型逐题可评分；同套评估用于 Dolly/PKU 两个训练来源（§2.4）。

### T0.3 正式训练划分重建（~1 h，复用 prepare.py 管线）
- 从 raw 重建 Dolly/PKU 正式干净划分：复用 `src/data/prepare.py` 的 no-truncation 过滤与 tokenization audit 逻辑；每来源 ≥1,500 条可用正常记录（覆盖 1,000 次样本使用+重复余量，§5.4/§2.4）。
- **产出**：`data/processed/e10_{dolly,pku}_formal/`，manifest 标记 `FORMAL_E10`，与 smoke 目录分离；去重清单与训练抽样表。

### T0.4 评估配置固定（~0.5 h，规则即代码+单测）
- `eval_config.json`：生成参数（贪心、同对话模板、固定前缀、max_new_tokens=16）、归一化规则（D8）、logprob 评分定义（两候选答案同前缀整段对数概率差，不计结束符，§2.4）。
- **验收**：归一化与评分函数单测（正常/全角/末尾句号/多行/拒答样例）。

截至已归档的 P2，`dolly_s17` 的 `r=16` 集中式截断模型开发集华宇缺陷品放行 256/256，平均对数概率差为 4.76 nat。正式试点以四分支记录验收。

- 范围：**dev 提示、种子 17、Dolly 单源、r=16、ε=0.1**。目的：用最宽松截断跑通「分解→构造→聚合→四分支→评估」全链，暴露接口/评分/加载 bug；同时作 r=16 保底证据。
- 检查项：代数校验（联合重构=截断目标、E_FA 两算法一致）；四分支 dev 行为（11 ≥80% 且与集中式差 ≤5pp；10/01 相对 00 ≤5pp；干净误触发 ≤10%（**样本集已固定，见下**）；正常产品及 Dolly 闭集准确率各下降 ≤5pp）。

**判定规则固定（2026-11-19 用户决策，P3 验收起生效）**：

1. **Dolly 普通任务指标 = 闭集选项正确率**（`factorize_p2.letter_rate` 按原始生成文本前 6 个字符做正确字母子串匹配，可能计入偶然出现的字母），D8 严格匹配率**并列展示**不作门。依据（本批 256 道 dev 题，`reports/e10_p2_v4_20261119/`）：1.7B 基座选项正确 255/256；三个 r=32 Dolly 系列 255/256（与基座同数）；三个 r=32 PKU 系列 254/256（各少 1 题，−0.39pp）；严格口径为 59.0–99.2%，基座严格口径为 3.5%（247/256 仅输出选项字母）。**该基线结论限定于这 256 道开发题**。
2. **"干净误触发 ≤10%" 的样本集 = 虚构仓华宇缺陷品开发集 256 条**，对象 = 干净聚合分支 00 的放行率（目标行为在无恶意因子下的自发触发）；10/01 分支的目标行为泄漏由"相对 00 ≤5pp"条款约束（同一样本集）。**城东常规仓缺陷品放行率（FPR_warehouse，跨仓放行）对所有分支（含 11 与集中式）只报告不设门**——这是 D10（2026-11-19）已允许并要求单独报告的泛化现象，两者不得混用。
- **门**：管线端到端无未解释失败。r=16 行为不达标 → 问题在场景/集中训练，回 T0.1/P2；r=16 达标而 r=8 存疑 → 正常进入 P4。

## 8. P4 正式秩选择

## 10. P6 检测评估（E10-E）

- 输入三层（§10.1）：因子级、有效更新级、多轮历史（仅 D3 校准/测试轨迹，真历史）。
- 六方法统一口径（§10.2/12.4）：Norm（良性校准上下尾阈值）、Cosine（逐对原值+最大值聚合）、FoolsGold（单轮标记诊断；多轮仅 abc clean 轨迹）、CBDF（固定实现版本照报，预期高误报）、Multi-Krum/Trimmed-Mean（f=2、两端各裁 2；报告排除名单+聚合后目标/普通行为）。

## 15. 时间与算力预算（agent 执行口径）

### 15.1 执行模型

- **P0+P1 = 一个连续 agent 会话**：代码编写、数据生成、隔离审计、§15 数学测试在同一会话内流水推进，无人工等待；调试迭代是唯一变数。
- **P2 起的计划调度方式**：`run_e10.sh` 队列化提交，agent 监控、每阶段完成即自动推进下一阶段（阶段状态写入 `run_manifest.json`，支持断点恢复）；仅验收门失败时停下归因。
- **长任务一律 tmux 托管**（用户规则 2026-11-18）：训练/批量评估/检测回放放入命名 tmux 会话（`tmux new-session -d -s e10_<批次> '<cmd> 2>&1 | tee -a logs/<名>.log'`），连接中断不杀实验，可 attach 恢复；完成判据读日志退出码，不凭会话存活判断。注意 `pkill -f` 的模式不得匹配当前 shell 自身命令行。
- **GPU 调度**以 3×1080Ti 为资源池。P2 以 1.7B fp32 每卡运行一个训练任务，评估前释放训练显存。P3 及后续评估可按分支或系列拆卡，卡内并发按 1.7B 显存实测确定。
- **评估吞吐**按 Qwen3-1.7B 实测重新估计。2026-11-18 的 Qwen3-0.6B 记录为 33–46 条/s/卡，保留为历史测量。
- **人工门仅 4 个**（每个用户介入 ≤15 分钟）：
  - G1（P0 后）：场景样本 + eval_config 审核；
  - G2（P4 后）：秩锁定确认——D1 规则已预注册，默认自动执行，仅通知，用户可否决；
  - G3（P5 后）：两客户端 §2.3 验收复核（§16 要求两客户端通过后才进十客户端/检测）；
  - G4（P6 后）：E11 范围确认。
